@votdev — thank you for pointing to openmediavault-mcp. I looked at it and the architecture is excellent for users who already have an LLM client configured — that is genuinely the better path for anyone who wants full OMV control from Claude or any MCP-compatible tool.

The design goal here is different. omv-agent is not backed by an LLM at all — the intelligence comes from three background daemons running continuously on the NAS itself. A probe daemon reads hardware state every 5 to 30 seconds — temperatures, RAID, bcache writeback status, disk usage, service health — writing structured data to a local SQLite database. A watcher daemon tails the systemd journal, monitors udev for block device changes, and diffs service states in real time, running with PrivateNetwork=yes and an empty capability bounding set so it cannot reach the network at all. A Flask API daemon maps natural language patterns to that live daemon data and a curated knowledge base. When a user asks whether bcache writeback is running, the answer comes from /sys/block/bcache0/bcache/writeback_running read seconds ago by the probe daemon — not from a model inference call. When a drive disappears from the block device list at 2am, the watcher fires an event and a badge lights up on the assistant button before the user notices anything is wrong.

The result feels like an AI assistant because it speaks in plain language about live system state, but the backend is three hardened daemons and a SQLite database, works fully air-gapped, and requires zero setup from the user beyond apt install. MCP with an external LLM gives you full control and is the right tool for capable users who want it. omv-agent gives any user — including those who have never heard of MCP — a self-contained assistant that opens when they click a button in their browser. Both are valid. They serve different users at different points on the comfort curve. That said, I would genuinely be interested in whether using the MCP RPC layer as a data source for the probe daemon makes sense — reading through the openmediavault-mcp interfaces rather than raw sysfs could be a cleaner integration long term.
